# 调用密钥的数据范围与接口权限

> 历史说明：本文引用的 evidence 文件、截图和日志仅本机保管，不随 Git 仓库分发；历史测试结果不代表本次或云端验证。

版本 1.5.0，数据库模式版本 5。功能面向管理员为不同店铺、渠道或负责人发放不同密钥，复用同一个已开放接口。经营看板仍是独立项目。

## 给店长创建密钥

1. 在“加工与开放”配置并启用销售额接口，决定输出列、日期范围查询方式、汇总指标、公式与排序。
2. 打开“调用密钥 → 创建调用密钥”，使用默认的“指定开放接口”方式，勾选允许调用的接口。
3. 对每张涉及的数据表设置“限定范围”。例如在同一个条件组内添加：渠道＝淘宝，店铺名称＝A店铺。使用字段中文说明辨认字段，值按来源原文精确填写。
4. 如需再开放京东的B店铺，添加另一个条件组：渠道＝京东，店铺名称＝B店铺。不要把两个渠道和两个店铺合并成独立的允许值列表，否则表达的是四种组合。
5. 检查授权摘要，填写名称、有效天数及调用频率后创建。完整密钥只显示一次，保存到调用系统服务端的安全配置中。

给B店长另外创建一把密钥，仍选同一个接口，只改变数据范围。不需要复制数据表或为每个店长建一套接口。

默认没有选中的接口，也没有默认放开的数据范围。需要访问整张表时，管理员必须显式选择“全部数据”。授权后找不到匹配数据时返回空结果，不自动扩大范围。该版本通过撤销旧密钥并创建新密钥调整授权，不提供原密钥就地编辑。

## 三种使用方式

| 方式 | 能访问什么 | 适用对象 |
|---|---|---|
| 指定开放接口 | 只能调用所选接口，查询结果受数据范围约束；不能直接查询底表 | 店长、渠道合作方、只需要固定指标的系统 |
| 按数据表查询（只读） | 能查询所选表的全部字段，但只返回授权范围内的数据；未授权的固定接口不能调用 | 需要自由明细或聚合查询的可信系统 |
| 完整数据表读写（高级） | 原版本的整表read/write授权；read也能调用该表的全部已开放接口 | 完整取数或分批导入系统 |

“数据范围”是行权限，“指定接口”约束可使用的查询规则。普通表读取授权仍覆盖该表全部字段；本版没有按任意字段逐列授予权限。接口中的字段、公式和筛选由管理员控制；接口在同一表上的规则修改会随接口生效。接口如果改为查询另一张表，原来绑定的受限密钥会被拒绝，必须重新发放。

## 数据范围怎么组合

- 一个条件中多个允许值为“任一个值匹配”。
- 同一个组内的条件为“全部同时匹配”。
- 多个组之间为“任一组匹配”。
- 数据范围与接口固定筛选、调用方传入筛选同时生效。调用方只能进一步缩小范围，不能覆盖管理员授权。
- 仅支持已声明为分组维度的文本字段；本版不支持通配符、模糊匹配、NULL授权、任意SQL或权限脚本。
- 精确匹配保留首尾空格。全空白、控制字符、重复值被拒绝。字段长度遵循数据表定义。

有多个渠道时，建议同组同时指定渠道和店铺名称；该表尚无独立店铺ID，单独使用店铺名称可能匹配到不同渠道中的同名店铺。

执行顺序：授权范围与原始筛选 → 分组汇总 → 指标公式 → 汇总后筛选 → 排序 → 分页。结果总条数与每日发布记录数也遵守数据范围。日发布版本标识和日期完整性仍表示所查询数据表的发布时间与可查询日期，不提供其他店铺的记录数。

例如退款率按授权范围内 `SUM(refund_amount) / SUM(pay_amount)` 计算，再按退款率排序。不会先算整张表的退款率再裁剪店铺。

## 接口契约

管理员创建密钥：`POST /api/v1/admin/keys`。以下服务和店名均为配置示例，实际使用时替换为已经保存的开放接口与来源原值。

```json
{
  "name": "A店长销售查询",
  "grants": {},
  "expires_in_days": 90,
  "requests_per_minute": 60,
  "policy": {
    "services": {"sales_summary": "ads_product_dashboard_daily"},
    "row_scopes": {
      "ads_product_dashboard_daily": {
        "mode": "filtered",
        "groups": [{"conditions": [
          {"field": "channel", "values": ["淘宝"]},
          {"field": "shop_name", "values": ["A店铺"]}
        ]}]
      }
    }
  }
}
```

调用方式仍为 `X-API-Key: <调用密钥>`，请求 `POST /api/v1/services/sales_summary/query`：

```json
{"start_date":"2026-09-01","end_date":"2026-10-22","limit":100,"offset":0}
```

无需把店铺筛选传给接口，服务自动从密钥中取得强制范围。即使调用方把店铺改为B店铺，最终也只能得到与授权范围相交的结果。限定接口密钥调用 `/api/v1/datasets/{slug}/query` 或 `/api/v1/query/batch` 会被拒绝。

`policy` 不为空时是受限只读密钥：

- `services` 是接口标识到数据表标识的绑定映射，最多100项。
- `grants` 可为空；如需通用表查询，可显式添加该表 `read`，不能包含 `write`。
- `row_scopes` 必须完整且恰好覆盖所有授权表，包括服务所用的表，不能遗漏或额外授权。
- `mode=all` 必须配空 `groups`；`mode=filtered` 包含1～20组，每组1～5个不重复字段条件，每个条件1～100个不重复文本值；整份policy最多2000个值。
- 创建时检查字段、类型、服务开放状态和绑定。查询时再次核验；保存的权限失效或损坏时拒绝访问，不回退为整表权限。
- `policy` 省略或为NULL时保留原版本的整表授权行为，`grants` 仍必须包含至少一张表。原有调用方请求协议保持兼容。

`GET /api/v1/admin/keys` 包含权限配置，只有管理员可访问；完整密钥及哈希不出现在列表中。`GET /api/v1/services` 仅返回当前密钥可调用的已开放服务。仅服务授权的密钥不能读取底表字段定义。撤销或过期后新请求被拒绝；已经开始执行的请求不承诺被主动取消。

## 升级与恢复边界

模式版本5只对 `api_keys` 增加可空的 `policy` 列；旧行保持NULL。没有改商品表、历史明细、发布版本、来源凭据、同步调度及同步引擎。

升级前确认没有运行中、排队或上传中的批次，备份数据库和代码；先在隔离库验证迁移与权限测试，再更新本机API与worker镜像。原始备份和配置加密密钥须安全保管，不包含在部署镜像和源码包中。

1.4.0要求模式版本4，不能仅切回旧镜像连接模式版本5的库。回滚须先保存升级后状态，再把升级前备份恢复到新的 `ds_restore_...` 数据库，使用1.4.0镜像和对应配置核对后切换。不要删除当前数据卷或在原库逆向删除字段。回滚后新增的受限密钥不会存在于升级前备份中，需保留新库及密钥使用记录供恢复。

实际测试、未验证边界和本地升级状态见 `evidence/permissions-delivery.json`，不能把本文的操作说明当成生产发布审批。
